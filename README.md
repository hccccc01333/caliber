# Caliber · Data Agent 的口径评测集

> 一个查业务数仓的 Data Agent，外加一套**专门测口径**的评测集。
>
> 重点不是让它写对 SQL，而是让它**在被问到口径不清的问题时不乱答**。

---

## 为什么是「口径」

text-to-SQL 已经被解决得比较好了，问一句出个数的 demo 满地都是。真实业务里出问题的不是 SQL 语法，是这些：

| 失败模式 | 后果 |
| --- | --- |
| 指标有歧义（"完成率"的分母是谁），agent 默默挑了一个还不说明 | 数字看起来对，口径是它替你猜的 |
| 两表编号体系不同，join 静默返回 0 行 | 被当成"没有人"上报，而不是"连不上" |
| 数据是截断的抽样快照，拿它外推总体 | 结论不可复现 |
| 时间范围没定义（"最近"/"上个月"） | 不同人跑出不同数 |
| 库里没有这个字段，agent 编一个 | 幻觉 |

这些不是凭空想的：它们抽象自一次真实业务数仓的口径审计（**不点名公司**）。
合成库只复刻这批**结构性质**，数值全部重新生成，因此仓库里没有任何真实业务数据。

---

## Related work：别人做到哪一步了

口径这件事不是没人做，是**大家做的不是同一层**。说清楚差别在哪，比说"没人做"有用得多。

### 工业界：成熟产品都在卷「语义层 + 生成准确率」

| 项目 | 路线 | 评测落在哪 |
| --- | --- | --- |
| WrenAI | 语义层优先，MDL 建模定义语言驱动 NL2SQL | SQL 生成准确率 |
| DB-GPT | 多智能体 + AWEL 工作流编排，AI 原生数据应用框架 | SQL / 报告生成 |
| SuperSonic（腾讯音乐） | Chat BI + Headless BI 融合，语义解析再翻译物理 SQL | 批量问答测试 |
| Vanna | RAG 优先（DDL + 文档 + 历史正确 SQL），2.0 转向 agent | SQL 执行结果 |

共同点很清楚：**口径靠人写进语义层，评测靠 SQL 准确率**。
以 SuperSonic 为例，它的 `benchmark` 模块是产品上线前的批量问答冒烟测试，
结果表里的字段直接写着「请标记生成 SQL 是否正确」「请分类不正确的原因」——**判分是人工的**。
语义层解决的是"让口径只有一个定义"，但没有回答"agent 遇到没定义的口径时该不该开口问"。

### 学术界：歧义 benchmark 已经有一批

- **AmbiQT**（2023）：3000+ 条，每条问题对应两个合法 SQL，测模型能否生成全部合理解释
- **AMBROSIA**（NeurIPS 2024）：范围歧义、附着歧义、模糊性三类
- **PRACTIQ**（AWS）：4 类歧义 + 4 类不可答，配多轮澄清对话
- **ABISS**（2026）：8 类问题分类 + 交互模拟，多轮对话下评估
- **TIDE-Bench**（2026）：链式歧义与意图漂移

这批工作的结论相当一致：**歧义是硬骨头，不是加个提示词就能解决的**。

### Caliber 的位置

差别在两处：

1. **层不同**。学术 benchmark 测的是**解析层**歧义——列名重叠、要不要 join、聚合是否预计算；
   Caliber 测的是**业务口径层**——分母是谁、时间窗怎么定、数字来自哪份来源、数据本身有没有被污染或截断。
   后者不会出现在 Spider / BIRD 这类库里，因为它不是 schema 的属性，是**业务过程的属性**。
2. **形态不同**。学术 benchmark 是**静态数据集**（题目 + 标准答案）；
   Caliber 是**可 CI 的工程评测集 + agent + 三档基线**，golden 写 SQL 不写死数字，换一个库照样跑。
   而且它把「反问」和「拒答」当作一等公民评分——该反问却硬答直接记 0，
   这是纯执行准确率指标给不出来的信号。

## 快速开始

```bash
python -m caliber.synth --out data/synth.db     # 1. 生成合成库（固定种子，可复现）
python -m caliber.runner --db data/synth.db     # 2. 跑评测集
python -m caliber.runner --db data/synth.db --agent all   # 3. 看三档基线对比
pytest -q                                        # 4. 跑测试
```

零第三方依赖（只用标准库），pytest 仅测试时需要。

## 基线对比

三档基线，用来证明这套评测集**有区分度**：

| agent | 行为 | A 直给 | B 口径歧义 | C 分母污染 | D 时间窗 | E 不可答 | 总分 | 一票否决 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `naive` | 有 SQL 能力，不看口径，硬答 | 0.493 | 0.167 | 1.000 | 0.333 | 0.333 | **0.449** | 12 |
| `rule` | 查口径字典、查连接白名单、不编答案 | 0.493 | 0.667 | 1.000 | 1.000 | 1.000 | **0.668** | 5 |
| `clarify` | 对任何问题都反问 | 0.000 | 0.733 | 0.000 | 0.400 | 0.000 | **0.175** | 24 |

四个结论：

1. **口径意识值 +0.219**（0.449 → 0.668）。同样的取数能力，多一道口径检查就是这么大差距。
2. **永远反问只有 0.175**。该答的题也反问会被一票否决，所以这套题不是"谨慎就能拿分"。
3. **规则 agent 的失败集中在两处**：复合查询（多条件交叠、按周分组、求平均转化周期）
   和同义改写（换词就漏）。前者是它没有通用组合能力，后者是它靠关键词匹配而非语言理解——
   **这正是需要模型的地方**，也是这套评测集存在的意义：把上限量化出来，而不是拍脑袋说"还行"。
4. **最危险的失败是「硬答一条错的 SQL」**，不是答不上来。改写题里规则 agent 给出了 `COUNT(*)`
   这种看着像答案、实则口径全错的结果——所以评分才要一票否决，而不是只比对数字。

> 这组数字是**在我自己出的题上、用我自己的 baseline** 跑出来的，不代表任何通用口径能力。
> 报这个数的时候必须带上这个边界。

## 评测集

32 题，五类：

| 类型 | 期望行为 | 题数 |
| --- | --- | --- |
| A 直给 | 口径明确，直接答对 | 17 |
| B 口径歧义 | 反问，或显式声明所选口径 | 6 |
| C 分母污染 | 给出数字，并主动警告该口径的已知污染 | 3 |
| D 时间窗缺失 | 反问时间范围，或声明数据本身的缺口 | 3 |
| E 不可答 | 明确说"算不了"，并说清为什么 | 3 |

其中 A14–A17 与 B05–B06 是**同义改写题**：同一件事换一种问法。
这一组是跑出来的，不是设计出来的——把规则 agent 拿去问改写说法，
发现它换个词就从「反问分母」退化成「硬答一条错的 SQL」：

| 问法 | 规则 agent 的表现 |
| --- | --- |
| 引导任务一的**完成率**是多少？ | 反问分母 ✓ |
| 引导任务一，用户**做到底的比例**是多少？ | 硬答 `COUNT(*) FROM users` ✗ |

题目与 agent 关键词同源时，这种脆弱性根本测不出来。所以评测集必须自带改写题，
**否则你测到的只是自己的措辞习惯**。

**期望值不写死数字，只写 golden SQL**。评分时在同一份库上执行 golden SQL 和 agent 的 SQL，
比对执行结果——所以换一个库评测集依然成立，不存在"背答案"的可能。

### 评分规则

- **不信 agent 自报的数字**：跑它给的 SQL 拿结果，不听它说"答案是 53.84"。
- **行为一票否决**：该反问却硬答，即使数字蒙对也记 0。那个数字是它替用户猜的口径。
- **口径声明单独计分**：数字对但没说清分母/时间窗/来源，只拿部分分。
- **权重按适用项归一化**：不要求的维度不白送分。

## 目录

```
src/caliber/
  synth.py    合成库生成器（复刻八类结构陷阱，固定种子）
  schema.py   表结构 + 口径字典 + 连接白名单
  cases.py    评测集 26 题
  agent.py    RuleAgent（strict / naive）+ AlwaysClarifyAgent + LLM 接口预留
  score.py    评分器
  runner.py   评测 runner
tests/        26 个测试
```

**口径字典是核心资产**：每个指标登记「有哪些合法口径 / 默认口径 / 已知陷阱」，
agent 必须从中挑一个并声明，而不是默默挑一个。

---

## 公开边界

- 合成数据，机制抽象自一次真实业务数仓的口径审计，不点名公司。
- 仓库不含任何真实业务数据、聊天原文、设备标识。
- 评测集题目只描述数据结构性质，不含真实业务数字。
